# Issue 规范

缺陷与需求一律登记在 GitHub Issue（`gh issue list`）。规范只服务一个目标：**看标题就知道是什么问题，看正文就能向上反馈**（对上能讲清影响，对自己能判定修没修好）。

## 一、标题

格式：

```
[类型] 对象：症状（触发条件）
```

| 段 | 要求 | 反例 |
| --- | --- | --- |
| 类型 | `[Bug]` `[Perf]` `[Enh]` `[Test]` 四选一 | `[问题]`、`fix`、无前缀 |
| 对象 | 模块或功能名，用使用者叫得出的名字 | `UpdaterManager`、`代码` |
| 症状 | 用户或工程师**能观测到的现象**，不写内部实现词 | `cancel() no-op`、`状态机竞态` |
| 触发条件 | 括号内写清何时出现；恒定出现可省略 | `（偶发）`——等于没写 |

**硬规则：标题里不许出现「优化、兼容、完善、若干、相关」这类空词。** 它们不描述现象，只描述心情。

### 正例

- `[Bug] OTA 安装：点「退出并安装」后旧进程不退出，升级失败（v1.2.0 → v1.3.0）`
- `[Bug] 大纲列宽：深层序号被截断显示不全（层级 ≥ 3 且同级条目 ≥ 10）`
- `[Test] OTA 下载用例：全量并发时 3s 窗口等不到下载态而假红`

### 反例

- `OTA 优化` —— 优化什么？谁看到什么现象？
- `修个 bug` —— 不可检索，也无法判断是否修好
- `cancel() no-op` —— 内部实现词，用户看不到，且没写触发条件

## 二、正文必填段落

按此顺序，用二级标题：

1. **现象** —— 一段话说清看到什么，带上数字（耗时、尺寸、条数）
2. **复现步骤** —— 编号步骤，第三人照做能重现
3. **预期** —— 契约出处（设计稿 / ADR / 用例名 / 上游 Issue）
4. **实际** —— 实际观测，与预期逐条对应
5. **环境** —— 版本号 + commit + macOS 版本 + 平台（arm64 / x86_64）
6. **证据** —— 日志、栈、文件路径、命令输出、截图；确实没有就写「未采集」并说明原因
7. **影响面** —— 谁受影响、阻塞什么（发版 / 用户数据 / CI / 无法验收）
8. **验收判据** —— **可判定**的完成条件：哪条用例由红转绿、哪个命令输出从什么变成什么

补充已有信息时**只补不删**：历史现场、排查方向、关联 Issue 都保留在正文里。

## 三、维护

- 有进展就追加到**同一个** Issue（`gh issue comment`），不新开重复条目。
- 关闭时写明 commit hash 与验证结论；判定非缺陷同样写明理由。
- 新建前先 `gh issue list --state open` 查重。
