## 2. 里面真正有什么（这张表决定我们怎么支持）

| 内容 | 数量 | 对 Kairo 的含义 |
| --- | --- | --- |
| **工作日历：周一至周六 6 天 × 8h** | 3 个日历（标准 / Project 98 基线 / 资源日历） | ⚠️ **最大冲突**。Kairo 现在按 7 天/周排期；同一份 100 天的任务，在 6 天工作周里是 117 个自然日 |
| 依赖 | 126 条，**全部 FS、零 lag** | 好办：单一类型，无需处理 SS/FF/SF 与 lead |
| **硬约束** | **97 条**（SNET 41 / FNET 56），其余 90 条 ASAP | ⚠️ 日期是**钉死**的，不是算出来的。Kairo 的约束是软约束（冲突只报警不改期），直接导入会得到一份「看起来对、其实不同」的排期 |
| 基线 | **4 个基线编号（0–3）、824 条基线记录** | Kairo 支持多基线，但同屏 3 条、8 色；4 条要处理超限提示 |
| **自定义域** | 4 个：`Text1=差异时间`、`Text2=关键任务`、`Date1=修改结束`、`Date2=修改开始`，**214 条任务有值** | ⚠️ 这是客户**真正的用法**：用 Project 跟踪「修改前后差异 + 关键任务标记」。这正是 Kairo 的基线偏差能力 —— 但我们没有这四个字段的落点 |
| 备注 | 12 条任务有 Notes（最长 52 字符） | 直接映射到 `notes` |
| 资源 | 1 个（无名称）、166 条分配 | 分配有意义（资源名为空），需降级为「未命名资源」 |
| 超链接 / 循环任务 / 子项目 | 0 | 不用管 |

## 3. 关键判断

1. **这份文件不是「计划」，是「承诺 + 差异台账」**：97 条硬约束把日期钉死，4 个自定义域记录改动前后的差异，4 条基线保留历史版本。第 3 条基线 + 差异时间字段，等价于 Kairo 的「基线偏差」——说明客户痛点和我们 1.0 做的事是同一件事。
2. **导入的第一道坎不是解析，是日历**：6 天工作周 vs Kairo 7 天日历天。不做换算，导入后所有日期要么全错、要么必须靠 97 条硬约束「焊」住（那等于把 Kairo 的排期引擎旁路掉）。
3. **硬约束的语义必须显式选择**：把 SNET/FNET 降级为 Kairo 软约束（会漂移），还是导入时钉成 `startDate`（保日期、但失去可重算性）。两者都要在预检里写清楚，不能替用户默认。

## 4. 建议的支持路线（三档，按投入排序）

| 档 | 做什么 | 能覆盖这份文件吗 | 人日 |
| --- | --- | --- | --- |
| **A（推荐先做）** | **读 MSPDI**（对方「另存为 XML」）+ 6 天工作周日历换算 + 硬约束降级策略 + 预检报告 | ✅ 能，且不碰任何法律灰区 | 10–12 |
| **B** | **写 MSPDI**（Kairo → XML），把 Kairo 的日历天写成 7 天工作周，基线写进 Baseline | ✅ 能，对方可在 Project 里打开 | 7–9 |
| **C（不建议）** | **直接读 .mpp 二进制** | ✅ 能，但代价是逆向 + 法律评估 | ≥60，且失败面不可控 |

对这份样本，A + B 就够：客户把 .mpp 另存为 .xml 是 10 秒操作，而我们不必维护四代容器的逆向代码。真正要补的能力是**工作日历**（F-22-06，此前列为 1.x 非目标）——不做它，导入任何 Project 文件都会失真。

## 5. 法律边界（框架，非法律意见）

**分三层看，风险完全不同：**

| 行为 | 风险 | 说明 |
| --- | --- | --- |
| 使用**微软公开的 MSPDI schema**（`mspdi_pj12.xsd`） | **几乎为零** | 微软自己发布的交换格式文档，明确用于第三方读写 |
| **观察用户自己的 .mpp 数据文件**、总结结构后自行实现解析 | **低到中** | 文件是用户财产；「看数据结构写解析器」属 interoperability（互操作），不是复制软件 |
| **反编译 / 反汇编 Project 程序本体**，或复制 MPXJ 的字段表/常量 | **中到高** | 这一层才真正触碰版权与商业秘密 |

法域差异（要点）：

- **中国**：《计算机软件保护条例》保护的是程序及其文档，**不延及思想、处理过程、操作方法**；第 17 条允许「为了学习和研究软件内含的设计思想和原理」而使用软件。互操作/兼容开发在司法实践中一般被容忍，但**没有像欧盟那样的明文豁免条款**，属于「有先例支持但需个案判断」。
- **美国**：`Sega v. Accolade`、`Sony v. Connectix` 确立「为互操作而进行的中间复制属合理使用」；DMCA §1201(f) 另有互操作例外。
- **欧盟**：2009/24/EC 第 6 条**明确允许**为互操作而反编译（合法持有、限于必要部分），且第 8 条禁止用合同排除该权利。

三个具体风险点，比「格式有没有版权」更现实：

1. **EULA**：微软软件许可通常禁止对**软件**反向工程。我们分析的是**用户的数据文件**，不是软件本体 —— 性质不同，风险显著低，但不是零。
2. **第三方库许可**：MPXJ 是 **LGPL-2.1**。把它链接进产品要遵守 LGPL（可替换、源码可得）；更关键的是**不能把它的字段表、常量、代码搬进我们的实现**，否则可能构成衍生作品。它适合做**内部验证工具**，不适合做产品运行时依赖。
3. **商标与陈述**：可以说「支持导入 MS Project XML」，不能说「Microsoft Project 官方兼容/认证」，也不要暗示背书。

**建议的合规做法（若真要做 .mpp 二进制）**：

- **Clean-room**：一组人只看「行为与数据样本」写出规格，另一组人按规格写代码，两组之间不共享代码；保留完整证据链（谁、何时、依据什么写的）。
- **只从用户自有文件与公开资料取证**，不反编译 Project 可执行文件。
- **上线前让法务出书面意见**，特别是面向中国客户销售、且宣传语出现「逆向/破解格式」这类词的时候。
- **产品默认路径仍是 MSPDI**：把 .mpp 解析做成「可选、离线、本地」，即便将来法律环境变化也能整块下线而不影响主功能。

## 6. 一句话结论

**这份文件能读、能导，但真正需要补的不是「解析 .mpp」，而是「工作日历 + 硬约束语义 + 自定义域落点」这三件事。** 建议按 A → B 推进，.mpp 二进制维持「不做」；法律上走 MSPDI 是干净的，逆向 .mpp 属「低到中风险、可做但要有 clean-room 与法务背书」。
